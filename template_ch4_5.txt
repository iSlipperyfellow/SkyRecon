[Heading3] Requirement Identifying Technique
[InfoBlue] This section describes the technique used to identify and document the functional requirements of the system.
[NormalWeb] For this project, Mockup-Based Requirement Analysis is used. In this approach, user interface mockups are created using UI/UX tools such as Figma, Adobe XD, or Balsamiq. These mockups visually represent how users will interact with the system. Functional requirements are then derived from each screen’s elements and behaviors.
[Heading4] Steps to Follow:
[NormalWeb] Identify key features and break them down into individual screens.
[NormalWeb] Assign a Mockup ID to each screen (e.g., M1 for Login Page, M2 for Dashboard).
[NormalWeb] Create mockups of the screens using any UI/UX design tool.
[NormalWeb] Identify interactive elements on each screen (buttons, forms, menus, etc.).
[NormalWeb] Derive a functional requirement from each element, describing what the system should do in response.
[NormalWeb] Organize all functional requirements using the table format provided in Section 2.2.1.
[NormalWeb] Backend Process Requirements
[NormalWeb] While mockups are effective for capturing frontend interactions, some system functionalities take place entirely at the backend (e.g., order processing, payment gateway callbacks, email/SMS notifications, scheduled jobs, data validation, account security, and real-time tracking in ride-hailing apps). In addition, there are systems that operate almost entirely at the backend with minimal or no user interface, such as traffic signal control systems or industrial monitoring systems.”.
[NormalWeb] To capture these processes, the Event–Response Table technique is used.
[NormalWeb] It is effective for modelling backend or real-time system behaviours where user interface interactions are not directly involved.
[NormalWeb] It describes the system’s response to specific events, often including conditions under which different actions occur.
[NormalWeb] This ensures backend workflows are captured in the requirements phase without going into design-level details.
[NormalWeb] For detailed guidelines and examples of both Mockup-Based Requirement Analysis and Event–Response Tables, please see Appendix A.

[Heading3] Reliability
[Header] Requirements about how often the software fails. The measurement is often expressed in MTBF (mean time between failures). The definition of failure must be clear. Also, don't confuse reliability with availability, which is quite a different kind of requirement.  Be sure to specify the consequences of software failure, how to protect from failure, a strategy for error detection, and a strategy for correction.
[Heading3] Usability
[Header] Usability requirements deal with ease of learning, ease of use, error avoidance and recovery, the efficiency of interactions, and accessibility. The usability requirements specified here will help the user interface designer create the optimum user experience.
[Header] Example:

[Pa1] State specific performance requirements for various system operations. [] Example:

[Heading3] Security
[Header] One or more requirements about protection of your system and its data. The measurement can be expressed in a variety of ways (effort, skill level, and time) to break into the system.  Do not discuss solutions (e.g. passwords) in a requirements document.

Data stores are not shown in the context diagram because they are contained within the system and remain hidden until more detailed diagrams are created.

[Heading2] General Coding Standards & Guidelines
[ListParagraph] Follow a consistent variable naming convention throughout the code. E.g.
[ListParagraph] Snakecase (words are delimited by “_” like: variable_one)
[ListParagraph] Pascalcase (words are delimited by capital letters like: VariableOne)
[ListParagraph] Camelcase (words are delimited by capital letters except the initial word like: variableOne)
[ListParagraph] Hungarian Notation (describes the variable type or purpose at the start of the variable name like: arrDistributeGroup)
[ListParagraph] Use naming that visually describes scope like privateField, Const etc
[ListParagraph] Use read only/immutable when a field’s value should not be changed after initialization
[ListParagraph] Use only get, for properties that should not be updated from outside
[ListParagraph] Name functions according to their functionalities.
[ListParagraph] Insert appropriate comments to make the code understandable to any reader. Additionally follow a consistent style to do so. E.g.
[ListParagraph] /* the below function will be used for the addition of two variables*/
[ListParagraph] int Add(){
[ListParagraph] //logic of the function
[ListParagraph] }
[ListParagraph] Avoid commenting on obvious things
[ListParagraph] Make use of indentation for indicating the start and end of the control structures along with a clear specification of where the code is between them.
[ListParagraph] Follow consistent naming convention for files and folders.
[ListParagraph] Follow proper structure for classes
[ListParagraph] Group code entities logically into projects/packages/modules/folders
[ListParagraph] Separate logical layers of application into different modules/services/utilities etc.
[ListParagraph] User separate files for each class, struct, interface, enum etc. Name of the file and the enclosing entity must be same. E.g., class Employee in Employee.cs/Employee.java
[ListParagraph] Define and use everything within the minimum scope possible
[ListParagraph] Use proper access modifier for all code entities if required
[ListParagraph] Code entities should have maximum cohesion and least coupling possible.
[ListParagraph] Follow DRY law.
[ListParagraph] Do not repeat code.
[ListParagraph] A piece of knowledge should exist only in one place within the codebase/application
[ListParagraph] Reuse code as much as possible
[ListParagraph] Always write short methods
[ListParagraph] Single method should not have too many logic, long conditional flow or too many parameters
[ListParagraph] Strictly follow Single Responsibility Principle (SRP) when writing methods, classes, modules, projects, packages, or any other code entities.
[ListParagraph] Write classes and other code entities that are easy to extend without modification.
[ListParagraph] Handle exceptions
[ListParagraph] Log exception and other significant event details
[ListParagraph] Follow a consistent convention for logging all over the application
