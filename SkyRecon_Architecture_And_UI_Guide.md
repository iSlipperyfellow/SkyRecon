# SkyRecon: Architecture, UI, and Integration Guide

This document provides a detailed breakdown of the SkyRecon system, covering the frontend user interface, the backend database schemas, the integration with the AirSim environment, and the Docker containerization strategy.

---

## 1. Frontend Interface (Next.js Dashboard)

The SkyRecon frontend is a React-based Single Page Application (SPA) built with Next.js and Tailwind CSS. The application is divided into several distinct tabs/pages, each serving a specific operational role.

### Detailed Tab Breakdown:

1. **Login (`login.tsx`)**
   * **Function**: Secure entry point for the application.
   * **Working**: Authenticates users against the Django backend. Upon success, it stores a JWT (JSON Web Token) in cookies or local storage. This token dictates the user's role (ADMIN, OPERATOR, ANALYST) and restricts access to certain tabs.

2. **Dashboard (`dashboard.tsx`)**
   * **Function**: The high-level executive summary view.
   * **Working**: Displays real-time KPIs (Key Performance Indicators) such as active drones, total detections today, active critical alerts, and system health. It features a miniature map widget for a quick glance at the current operational area.

3. **Mission Control (`mission-control.tsx`)**
   * **Function**: Command and control center for active drone flights.
   * **Working**: Allows operators to assign drones to specific flight paths. Features operational buttons like **Start**, **Pause**, **Resume**, and **Abort**. It communicates with the backend via REST API to update the `Flight` status, which is then picked up by the AirSim integration script to physically alter the drone's behavior in the simulation.

4. **Live Feed (`live-feed.tsx`)**
   * **Function**: Real-time First-Person View (FPV) from the drone.
   * **Working**: Connects to the backend via WebSockets to receive a continuous stream of image frames. The YOLOv8 inference bounding boxes (metal, plastic, organic) are overlaid on this feed dynamically, allowing operators to visually confirm hazards as the AI detects them.

5. **Hazard Map (`hazard-map.tsx`)**
   * **Function**: Full-screen geospatial awareness tool.
   * **Working**: Uses `react-leaflet` to render a map containing the Runway polygons. As telemetry comes in via WebSockets, the drone's marker moves across the map. Detections are plotted as pins (Red, Yellow, Green based on the hazard score). Includes heatmap layers (via `leaflet-heatmap`) to show areas with historical debris accumulation.

6. **Alerts (`alerts.tsx`)**
   * **Function**: Actionable notification center.
   * **Working**: Lists all medium and high-risk hazards. Operators use this tab to review a detection, assess the image, and click "Acknowledge" to mark the hazard as reviewed in the database.

7. **Analytics (`analytics.tsx`)**
   * **Function**: Historical data review and reporting.
   * **Working**: Utilizes `Chart.js` to render bar charts, line graphs, and pie charts showing debris trends over time (e.g., most common material type, busiest days). Allows Analysts to generate and export PDF/CSV reports.

8. **Models (`models.tsx`)**
   * **Function**: AI model management.
   * **Working**: Displays the current active YOLOv8 model, its accuracy metrics, and allows administrators to track different training iterations or swap the active model.

9. **Admin / Settings (`admin.tsx`, `settings.tsx`)**
   * **Function**: System configuration and user management.
   * **Working**: Admins can create new user accounts, assign roles, define new Runway geofences, and configure system endpoints (like the MQTT broker address or Inference URL).

## 2. Backend Architecture (Django Python Models)

The Django backend (`backend/core/models.py`) uses PostgreSQL with the PostGIS extension to handle standard relational data alongside complex spatial data.

### Core Models & Relationships:

* **`User`**: Custom user model extending Django's standard auth. Includes a `role` field (ADMIN, OPERATOR, ANALYST) for Role-Based Access Control (RBAC).
* **`Drone`**: Represents the physical (or simulated) UAV asset. Tracks the `identifier` (e.g., Drone-001), `max_payload`, current `status` (Active, Inactive, Maintenance), and `home_location` as a spatial Point.
* **`Flight`**: Represents a specific mission. Linked to a `Drone`. Stores the `mission_name`, `start_time`, `end_time`, and the `path` (as a PostGIS `LineStringField`). Tracks the mission `status` (Planned, Active, Aborted).
* **`Telemetry`**: High-frequency data generated by the drone. Links to the `Drone` and `Flight`. Stores `timestamp`, `location` (PointField), `altitude`, `velocity`, `heading`, and `battery`.
* **`Detection`**: Created when the YOLOv8 model finds debris. Stores the `bbox` (bounding box), `label` (e.g., metal), `confidence` (0.0 to 1.0), and the exact geographic `geometry` (PointField) of where the debris is located.
* **`Hazard`**: A one-to-one extension of `Detection`. Contains the calculated risk `score` and `level` (LOW, MEDIUM, HIGH) based on the material type and proximity to the runway. Tracks if an operator has `acknowledged` the hazard.
* **`Runway`**: Stores the airport infrastructure. The most critical field is `geometry` (a `PolygonField` representing the runway boundaries). This is used in spatial queries (e.g., `distance_lte`) to calculate if debris is a high risk.
* **`InferenceJob`**: A tracking model for the async image processing pipeline. Ensures no frames are lost between the drone, the Django backend, and the YOLO inference service.
* **`NavigationPlan`**: Stores planned routes and geofence constraints.
* **`AIModel`**: Tracks different versions of the YOLO/PyTorch models, their framework, and deployment status.

## 3. AirSim Integration

Microsoft AirSim (Unreal Engine) serves as the high-fidelity simulation environment for the drone, replacing the need for physical drone hardware during development and testing.

### How it Connects to SkyRecon:
1. **The Bridge Script (`drone_simulator.py`)**: A standalone Python client utilizing the `airsim` Python library connects to the local Unreal Engine instance.
2. **Telemetry Extraction**: The script continuously pulls the drone's position (converting AirSim's NED local coordinates to global GPS coordinates), altitude, and velocity, and publishes this payload to the Mosquitto **MQTT Broker**.
3. **Vision Stream**: The script captures images from the simulated drone's downward-facing camera and sends them to the backend API or inference service for YOLOv8 object detection.
4. **Command Execution**: The script polls the backend (or listens via WebSockets) for flight commands triggered by the frontend `mission-control.tsx`.
   * If an operator clicks **Start**, the script commands the AirSim drone to take off and follow the `NavigationPlan` waypoints.
   * If an operator clicks **Abort**, the script instantly halts the drone's current path.
5. **Autonomous Behaviors**: The integration includes logic for collision avoidance within the simulated city environment and triggers an autonomous Return-To-Base (RTB) protocol when the simulated battery level drops below a critical threshold.

## 4. Docker Containerization Strategy

The entire project is orchestrated using `docker-compose`, ensuring the system runs identically on a developer's laptop, in testing, and in production. 

### The Container Ecosystem (`docker-compose.yml`):

1. **`db` (PostGIS)**: The foundation. Runs PostgreSQL 15 with the PostGIS 3.3 extension pre-installed. All geographic calculations rely on this container.
2. **`rabbitmq`**: The message broker that allows Django Channels to broadcast WebSocket messages (like live telemetry and new detections) to multiple connected frontend clients simultaneously.
3. **`mosquitto`**: The Eclipse Mosquitto MQTT broker. Highly optimized for IoT devices. The AirSim script publishes here, and the Django backend subscribes to ingest the data.
4. **`backend`**: The main Django application running via Gunicorn/Daphne. Handles REST API requests, database migrations, and WebSocket connections.
5. **`inference-mock`** *(or production AI container)*: A decoupled Python service (usually FastAPI) that holds the PyTorch/YOLOv8 environment. By isolating the AI, the heavy processing doesn't block the main Django web server. Can be allocated GPU resources via Docker's `--gpus all` flag.
6. **`frontend`**: The Next.js Node.js server. Pre-renders the React pages and serves the dashboard to the user's browser on port 3000.
7. **`pgadmin`**: A web-based GUI for developers to inspect the PostgreSQL database visually without using command-line SQL.

**Deployment Flow:**
Running `make up` or `docker-compose up -d` creates a private Docker network (`skyrecon-net`). The containers communicate securely via internal DNS (e.g., the backend connects to the database using the hostname `db` rather than an IP address).
