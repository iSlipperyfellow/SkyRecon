[] Executive Summary
[NormalWeb] SkyRecon is a state-of-the-art drone platform driven by artificial intelligence that raises the aviation safety bar sky high. It can now independently detect and analyze foreign object debris (FOD) present on airport flight paths. The debris may attract birds lint and lead to catastrophic consequences like a flight delaying discrepancy, equipment damage, and possible safety concerns. Traditional manual inspection methods are
[NormalWeb] slow and resource-consuming as well as variable. SkyRecon attaches the temporal and spatial issues related to waste disposal through a combination of computer vision, reinforcement learning, and communication technologies in the cloud which provide a scalable, real-time, automated solution.
[NormalWeb] The structure of the suggested system is based on two modes — simulation and hardware. In the former case, simulated drones are used within an environment like AirSim to ensure safe training and evaluation of the AI models. Because of this, the agents of reinforcement learning can create the highest possible navigational and coverage policies using algorithms like Proximal Policy Optimization (PPO) and Deep Deterministic Policy Gradient (DDPG). In the hardware mode, real drones establish a secure communication protocol like MQTT or WebSocket that connects to a cloud inference backend. The drones capture live video and stream it to the cloud, which performs the AI-based debris detection using YOLOv8, a state-of-the-art object detection model.
[NormalWeb] Once the debris is detected, skyRecons Geospatial Mapping Module presents the results with a dynamic map interface. Each detection event is tagged with geographical coordinates, confidence levels are annotated, and material types are classified. Hazard Analysis Module is the one to determine the level of severity by means of debris and the distance to critical flight areas. All of this information is consolidated into a centralized web dashboard used as the main control panel for the airport. The dashboard features live telemetry of the drone, detection overlays, hazarding analytics, and alert notifications which rather easy the transmission of response actions.
[NormalWeb] The structure of SkyRecon is modular, cloud-based architecture allowing effortless scalability, fault tolerance, and integration of existing airport programs. It also considers regulations on safety issues like geofencing, altitude limits, and emergency handling to comply with UAV operational guidelines. The dual nature of the system, it is both a research-oriented simulation and a piece of hardware to be deployed, it links the gap between academic innovations and real-world aviation applications.
[NormalWeb] SkyRecon is on the forefront of the implementation of AI-backed ways of measuring dangers in flight paths, providing real-time feedback through visualization, and a change in the airport’s approach to the security of operations, all at the same time.
[] Abstract
[] SkyRecon's main purpose is to pioneer the way to more safety in aviation by leveraging the power of technological solutions like artificial intelligence and drone to detect debris on airport runways and flight paths automatedly. The prevailing systems are heavily dependent on manual inspection, and besides that, they have stationary surveillance cameras which have a limited field of view, and they react slowly. The human factor is also one of the major contributors to the errors. The current debris management practices lack the ability to provide real-time data analytics and independent vehicle integration for the method of hazard detection being difficult. SkyRecon approaches these problems by the means of a smart, cloud-based drone infrastructure that could work autonomously, offer immediate debris categorization, and create hazard visualization. The project is dedicated to providing a scalable, fully-autonomous runway monitoring system that can change from virtual to actual hardware environments easily. The pivotal missions are to create an AI vision model for YOLOv8-based debris detection, to make optimal path planning of drone flights using reinforcement learning algorithms, and to secure cloud communication framework with live data for streaming and analysis. Furthermore, the project intends to generate geospatial heatmaps and provide airport authorities with actionable hazard insights through a web dashboard. In the end, the value of the project will be in the enhancement of the airport's operational safety, the reduction of the manual activity, and elimination of bird strikes by a reliable, intelligent, and entirely autonomous aerial monitoring system.

[] Chapter 1: Introduction and Problem Definition
[] 1.1 Overview of the Project
[] SkyRecon is a drone system, fully auto driven by AI for the autonomous detection and classification of debris on airport flight paths. It is based on computer vision for object recognition and reinforcement learning for a fully optimized flight path coverage. The entire system simulates both drone environments that are integrated via cloud communication and the actual physical drone environments, which makes it cloud-based and allows users to switch easily between testing and real-life deployment.
[] 1.2 Vision Statement
[] The SkyRecon System is a suitable solution for AI-powered drones and cloud-based monitoring for runway maintenance teams and airport safety authorities who require a quick, more accurate, and continuous remediation on debris hazards in flight paths. It is the first product on the market that is capable of real-time, autonomous classification, and mapping of runway debris.It does not rely on traditional manual inspections, fixed CCTV cameras, or costly ground-based radar systems. Instead, our product delivers scalable, autonomous, and intelligent debris detection with little human intervention and the highest possible operational safety through artificial intelligence, reinforcement learning, and cloud communication.
[] 1.3 Problem Statement
[] Airports are grappling with the problem of operational safety due to foreign object debris (FOD) that are some of the materials deposited on the airstrip. These can be metallic, plastic waste, or food sources that can attract birds. Manual inspections are labor-intensive, error-prone, and subject to human limitations. The absence of continuous automatic monitoring leads to bird strikes and potentially aircraft harm.
[] 1.4 Proposed Solution
[] SkyRecon makes use of autonomous drones which have onboard cameras and a cloud-based AI inference system. The drones perform live video capturing which is sent to a central server where the debris is detected using YOLOv8 in real time. The debris that is found is categorized by the type of material, geotagged, and presented on an interactive dashboard. Reinforcement learning models are responsible for the optimal flight path and the coverage while a safety module oversees the compliance of geofencing and emergency protocols.
[] 1.5 Objectives
[] BO-1: Decrease the time and labor costs of manual runway debris inspection by at least 60% through an autonomous drone surveillance system.
[] BO-2: Enhance the precision of debris detection and classification by 30% compared to the manual visual inspections through AI-based object recognition.
[] BO-3: Lessen the average runway downtime by 25% due to debris-related incidents through the faster detection and alert generation process.
[] BO-4: Integrate real-time cloud-based hazard monitoring for continuous visibility of runway conditions.
[] BO-5: Automate debris tracking, reporting, and archival logging processes to ensure regulatory requirement compliance in the airport.
[] BO-6: Name a modular simulation-to-hardware framework that will decrease the cost of testing and accelerate the deployment of AI models to actual drones.
[] 1.6 Scope
[] The system is based on both simulation and hardware drone operation modes. The simulation uses AirSim and Gazebo environments for both training and evaluation. The hardware implementation is by drone–cloud communication via API for live inference. The web dashboard displaying the detections, analytics, and hazard visualization consolidates the UI and ensures multi-drone systems as well as different airport layouts are scalable.
[] 1.6.1 Limitations / Constraints
[] Weather Dependence: High-wind or rain may affect flight stability and image quality.
[] Communication Latency: Cloud inference delays may slightly impact real-time response.
[] Regulatory Constraints: Flight testing must comply with UAV operation laws and restricted airspace regulations.
[] Power Limitations: Drone battery life limits continuous operation duration.
[] Lighting Conditions: Poor visibility may cause the detection rate to be low.
[] 1.7 Modules
[] The proposed SkyRecon system is implemented using a modular architecture that abstracts functionalities into separate components that are interconnected but independent. Each module affects a specific operational aspect, thus ensuring scalability, maintainability, and clear data flow between the Drone System, Cloud Backend, and Web Dashboard Interface.

[] 1.8 Related Systems
[] 1.8.1 Literature Review
[] A thorough review of the recent advancements in AI-driven aerial monitoring shows significant developments in object detection, reinforcement learning, and autonomous UAV operations.Early vision-based debris detection used classical image processing methods such as edge detection and contour analysis (Szeliski, 2010), which resulted in a high sensitivity to lighting variances. The arrival of deep learning models like YOLO and Faster R-CNN (Ren et al., 2015) opened up a new world for automation of object recognition and, in turn, made very effective real-time, high-accuracy detection work for UAVs.
[] In the UAV domain, the research presented by Shah et al. (2018) in AirSim, a physics-based simulation scheme designed for safe and realistic training of aerial agents, was a breakthrough. Expanding on that, reinforcement learning algorithms like DDPG (Lillicrap et al., 2015) and PPO (Schulman et al., 2017) have been efficiently applied to navigation and path optimization tasks. These technologies give drones the ability to determine optimal routes for debris inspection while using less energy.
[] Cloud–drone integration has also been a focus area. Projects such as Gupta et al. (2022) and Kovacs et al. (2021) demonstrated AI inference in the cloud for drones, showcasing reduced computational requirements on-board and faster updates. Nevertheless, most previous setups are either in simulated environments or unproven hardware conditions.
[] SkyRecon addresses this gap by offering a hybrid simulation–hardware environment where cloud communication allows for seamless transition from virtual models to physical drones. This makes deployment faster, cheaper, and safer, representing a major advancement in intelligent UAV-based inspection systems.

[] 3.1 Introduction
[] This chapter describes the overall design of the SkyRecon system. It includes the architectural design, UML-based system modeling, database structure, and interface-level details. The design ensures that all functional and non-functional requirements identified in earlier chapters are supported through a modular, scalable, and maintainable system architecture.
[] 3.2 System Architectural Design
[] 3.2.1 System Architecture Overview
[] The SkyRecon system architecture is designed as a distributed, cloud-based platform that integrates autonomous drone operations, AI-powered debris detection, and real-time geospatial visualization. The architecture follows a multi-layered approach where each layer encapsulates specific responsibilities, enabling scalability, maintainability, and seamless integration between hardware, cloud services, and user interfaces.
[] The system operates in two distinct modes: Simulation Mode and Hardware Mode. In Simulation Mode, virtual drones operate within physics-based environments (AirSim/Gazebo) to train reinforcement learning agents and validate AI models in a safe, controlled setting. In Hardware Mode, physical UAVs equipped with cameras, GPS, and IMU sensors execute real-world missions, streaming live video to cloud-based AI inference engines for debris detection and classification.
[] The architecture is organized into four primary layers: the Frontend Web Application Layer, the Backend Services Layer, the Service Layer, and the Data Storage Layer. The Frontend Layer provides airport personnel with an interactive dashboard for monitoring missions, viewing live detections, analyzing hazard maps, and generating reports. The Backend Services Layer coordinates all business logic, API endpoints, authentication, and communication orchestration between drones and cloud modules. The Service Layer contains specialized microservices responsible for drone control, AI processing, reinforcement learning navigation, real-time communication, hazard analysis, and security enforcement. Finally, the Data Storage Layer manages persistent storage using PostgreSQL with PostGIS for relational and geospatial data, cloud file storage (AWS S3/Azure Blob) for video recordings and model weights, and mapping services (Leaflet.js/Mapbox) for rendering interactive hazard visualizations.
[] Data flows through the system in a structured pipeline: drones capture live video feeds and transmit them via encrypted MQTT or WebSocket protocols to the Backend Services Layer. The AI Processing Module receives video frames, performs real-time inference using YOLOv8, and returns detection results with bounding boxes, confidence scores, and debris classifications. The Hazard Analysis Engine evaluates each detection, assigns risk scores based on debris type and proximity to critical flight zones, and triggers alerts when necessary. All detection metadata, telemetry logs, and mission records are stored in PostgreSQL, while raw video and images are archived in cloud storage. The Frontend Dashboard continuously polls the backend via REST APIs to update mission status, display live detection overlays on maps, and present analytics to users.
[] Security is enforced at every layer through multiple mechanisms. Communication between drones and cloud servers uses TLS 1.3 encryption to prevent data interception. User authentication relies on OAuth 2.0 with JWT session tokens, ensuring only authorized personnel can access sensitive operations. The database employs AES-256 encryption at rest, and all API endpoints enforce role-based access control (RBAC) to restrict functionality based on user roles (Admin, Operator, Analyst). Additionally, the system implements geofencing constraints and emergency protocols to ensure safe drone operations and prevent unauthorized airspace entry.
[] The architecture's modular design allows individual components to be updated, replaced, or scaled independently without disrupting other services. For instance, the AI Processing Module can be upgraded to newer detection models without modifying the drone communication or database layers. Similarly, the system supports horizontal scaling by deploying multiple backend instances and load balancing requests across them, enabling concurrent operations for multiple drones simultaneously.

[] 3.3 Architecture Style / Pattern
[] The SkyRecon system follows a Layered Architecture Pattern (specifically a Cloud-Robotics N-Tier Architecture). This pattern is essential for separating the robotic hardware control from the heavy computational logic required for AI inference, ensuring that the drones remain lightweight and agile while the cloud handles processing.
[] 3.3.1 Guidelines for Students
[] Selected Pattern: Layered Architecture (Cloud-Robotics Hybrid)
[] Justification for Layered Architecture:
[] Computational Offloading: SkyRecon requires heavy AI processing (YOLOv8 detection, RL path planning). A layered approach allows these resource-intensive tasks to run on the Service Layer (Cloud) rather than draining the drone's onboard battery.
[] Scalability: The architecture supports multiple drones connecting to a single backend. The Service Layer can scale horizontally to handle video streams from a fleet of drones without requiring hardware upgrades on the UAVs themselves.
[] Modularity: The distinct separation between the Hardware Layer (Drone/Simulation) and the Business Logic Layer allows the team to switch between the AirSim simulation environment and physical UAVs without rewriting the core application logic.
[] Security: By isolating the Data Storage Layer behind the Backend Services Layer, the system ensures that flight logs and hazard maps are protected from direct unauthorized access .
[] Layer Descriptions:
[] Layer 4: Frontend Layer (Presentation)
[] Responsibility: Provides the interactive web dashboard for Airport Safety Officers and Drone Operators. It visualizes live telemetry, hazard maps, and alerts.
[] Components: React.js Web Application, Leaflet.js/Mapbox Geospatial Viewer, Redux State Management.
[] Interaction: Sends REST API requests to Layer 3 and subscribes to WebSocket feeds for real-time video updates.
[] Layer 3: Backend Services Layer (Business Logic)
[] Responsibility: Acts as the central controller/orchestrator. It authenticates users, manages mission states (Start/Pause/Return), and routes data between the drones and the AI engines.
[] Components: Flask/FastAPI (Python), Authentication Service (OAuth 2.0), Mission Controller, Alert Manager.
[] Interaction: Validates incoming telemetry, enforces geofencing rules, and coordinates with Layer 2 for AI analysis.
[] Layer 2: Service Layer (AI & Control)
[] Responsibility: Handles the intelligent processing. This includes detecting debris in video frames and calculating optimal flight paths.
[] Components: AI Inference Engine (YOLOv8), RL Navigation Module (PPO/DDPG), Hazard Analysis Engine, Communication Broker (MQTT).
[] Interaction: Processes raw video data and returns structured JSON (bounding boxes, confidence scores) to Layer 3.
[] Layer 1: Data Storage & Infrastructure Layer
[] Responsibility: Persists all system data.
[] Components: PostgreSQL (Structured Data), PostGIS (Geospatial Data), Cloud Storage (Video Archives/Model Weights).
[] Interaction: Accessed only by Layer 3 for saving logs and retrieving historical data.
[] 3.3.2 Component Interaction
[] The layered architecture facilitates a secure, bidirectional flow of data between the physical/simulated drones and the user interface.
[NormalWeb]   Drone Telemetry & Video Uplink: The Hardware/Simulation Layer (Layer 1 extension) captures live video and flight data (GPS, Battery). This is transmitted via MQTT/WebSocket to the Service Layer. The Communication Broker creates a low-latency pipe, ensuring the video reaches the AI engine with minimal delay.
[NormalWeb]   AI Inference & Hazard Logic: The Service Layer processes the incoming video frames using YOLOv8. It detects Foreign Object Debris (FOD), classifies it (Metal, Plastic, Organic), and calculates a confidence score. Simultaneously, the Hazard Analysis Engine checks the GPS coordinates against the runway map to determine risk levels. These results are sent up to the Backend Services Layer .
[NormalWeb]   Dashboard Visualization & Control: The Backend Services Layer pushes the processed results (Debris detected at Lat/Long X,Y) to the Frontend Layer (React). The dashboard renders a marker on the Leaflet 3D Map. Conversely, when an operator clicks "Return to Home" on the dashboard, the command flows down through the Backend, to the Service Layer, and finally to the Drone via MAVLink .
[NormalWeb]   Data Persistence & Security: All detection events and mission logs are securely stored in the Data Storage Layer. PostGIS handles the spatial queries for the map, while Cloud Storage archives the raw video evidence. OAuth 2.0 ensures that only authorized personnel can access these records or control the drones.

[] Purpose: The class diagram defines the static structure of the SkyRecon system, illustrating the primary classes, their attributes, methods, and relationships. It serves as a blueprint for the object-oriented design, ensuring modularity and a clear separation of concerns between the physical drone hardware, cloud-based AI services, and user management modules.
[] Key Classes:
[] User: Stores authentication credentials and contact details. It serves as the base class for Operator, SafetyOfficer, and Admin, implementing core login and role-based access control functionalities.
[] Operator: Extends User and includes specific permissions for mission control. Operators can initiate drone flights, view live telemetry, and receive operational alerts.
[] SafetyOfficer: Extends User and focuses on hazard management. Safety Officers receive critical FOD alerts, view hazard maps, and can authorize emergency runway clearing operations.
[] Admin: Extends User with system-wide privileges. Admins manage user accounts, configure fleet settings, oversee system health, and access audit logs.
[] Drone: Represents the physical or simulated UAV. It manages hardware-specific attributes like battery level, GPS location, altitude, and connection status. It supports methods for takeoff, landing, and waypoint navigation.
[] Mission: Links a Drone to a specific FlightPath and Operator. It tracks the mission's lifecycle (Scheduled, Active, Completed, Aborted) and logs performance metrics like duration and coverage area.
[] Detection: Stores individual instances of AI-identified debris. Attributes include the debris type (Metal, Plastic, Organic), YOLOv8 confidence score, timestamp, and precise geospatial coordinates.
[] HazardMap: Aggregates multiple Detection objects to visualize risk zones. It provides methods to generate heatmaps and calculate the severity of hazards based on their location relative to the runway.

[] YOLOv8: Extends AIModel specifically for object detection. It implements the logic to process video streams and identify bounding boxes for potential debris.
[] RLAgent: Extends AIModel for autonomous navigation. It utilizes reinforcement learning algorithms (like PPO or DDPG) to calculate optimal flight paths and avoid obstacles.
[] FlightLog: Archives telemetry and event data for post-mission analysis. It ensures compliance with aviation regulations by maintaining a complete history of the drone's actions.

[] 3.5 Data Design
[] 3.5.1 Information Domain to Data Structure Transformation
[] The information generated and consumed by the SkyRecon system is transformed into three primary types of data structures:
[] Relational & Geospatial Data: Structured telemetry data, user profiles, mission logs, and geospatial coordinates (latitude/longitude/altitude) of detections are stored in a relational database augmented with spatial extensions (PostgreSQL + PostGIS). This ensures transactional integrity and supports complex spatial queries necessary for map rendering and proximity analysis.
[] Streaming Data: Raw video feeds and high-frequency telemetry are handled as streams via MQTT/WebSocket and temporarily stored in a cache before being processed by the AI inference service.
[] Unstructured Data: High-resolution raw video archives, detection snapshots (for audit trail), and AI model weights (YOLOv8, RLAgent) are stored as large binary files in Cloud File Storage (AWS S3 / Azure Blob).
[] 3.5.2 Major Data Entities
[] The SkyRecon system is organized around the following major data entities, corresponding to the tables in the D2: Mission Logs and D3: Hazard DB data stores:
[] Mission
[] Description: Represents a scheduled or active drone surveillance flight over a designated runway area.
[] Storage: missions table.
[] Key Attributes: Mission ID (Primary Key), Drone ID (Foreign Key), Start Time, End Time, Status (Active/Complete/Aborted), Coverage Area.
[] Drone
[] Description: Represents the physical or simulated Unmanned Aerial Vehicle (UAV).
[] Storage: drones table.
[] Key Attributes: Drone ID (Primary Key), Model Type, Current Status (Idle/Flying), Battery Health, Last Maintenance Date.
[] Detection
[] Description: An instance of Foreign Object Debris (FOD) confirmed by the AI model.
[] Storage: detections table (D3: Hazard DB).
[] Key Attributes: Detection ID (Primary Key), Mission ID (Foreign Key), Geospatial Location (PostGIS Point), Debris Type (Metal, Plastic, Organic), YOLOv8 Confidence Score, Hazard Score (1-10), Snapshot URL.
[] TelemetryLog
[] Description: High-frequency records of the drone's position and status throughout a mission.
[] Storage: telemetry_logs table (D2: Mission Logs).
[] Key Attributes: Log ID (Primary Key), Mission ID (Foreign Key), Timestamp, GPS Coordinates, Altitude, Velocity, Signal Strength.
[] Chapter 4: Implementation
[] This chapter discusses the implementation details of the SkyRecon project. The system is built using a Cloud-Robotics hybrid architecture, consisting of a Django (Python) backend for core logic and geospatial processing, a Next.js (React) frontend for the command center, and an edge-deployed hierarchical AI engine for real-time debris detection and classification.
[] 4.1 Project Methodology & Algorithms
[] This section explains the step-by-step approach and core algorithms that power SkyRecon. The methodology focuses on the pipeline from data acquisition by autonomous drones to actionable intelligence on the dashboard.
[] 4.1.1 Project Methodology (Step-by-Step Approach)
[] The implementation of SkyRecon followed a structured pipeline consisting of data collection, a two-stage deep learning analysis, and real-time hazard mapping.
[] 1. Data Collection & Unification
[] What: Aerial imagery of runway debris (FOD) and drone telemetry data.
[] How:
[] Synthetic Data: Generated using AirSim to simulate diverse debris under various lighting conditions.
[] Public Datasets: Aggregated datasets including TrashNet, UAVVaste, Airport Runway Debris Dataset, and YOLOv8 Trash Dataset.
[] Normalization: All disparate labels were mapped to a single class ("trash": 0) to create a robust, unified training set for the primary detector.
[] Why: Decoupling detection from classification maximizes accuracy and allows for scalable expansion of material types without retraining the entire pipeline.
[] 2. Data Preprocessing & Augmentation
[] Frame Extraction: Live video streams (30 FPS) were sampled to extract keyframes.
[] Normalization: Input images were resized to 640x640 pixels and normalized (0-1).
[] Advanced Augmentation: Applied random rotation (±45°), scaling, brightness variation, Gaussian noise, motion blur, and mosaic augmentation to handle camera altitude and environmental lighting variations.
[] 3. Feature Extraction & Hierarchical Analysis
[] Stage One (Detection): A YOLOv8 model identifies and localizes potential debris, generating bounding boxes for all "trash" objects.
[] Stage Two (Classification): A specialized CNN (MobileNetV2/ResNet18) analyzes the cropped regions from Stage One to classify the material type (metal, plastic, organic, etc.).
[] 4. Machine Learning Model Training
[] Architecture: A two-stage hierarchical deep learning architecture.
[] Training:
[] Stage 1 (YOLOv8): Trained on the unified dataset (80% train / 20% val) for 60 epochs with early stopping.
[] Stage 2 (Classifier): Trained on a smaller, manually labeled dataset of cropped debris images using transfer learning.
[] Why: This modular approach improves robustness and allows for easier upgrades to the classification logic.
[] 5. Real-Time System Integration
[] Communication: Django Channels and RabbitMQ handle asynchronous WebSocket connections for live telemetry.
[] Geospatial Engine: PostGIS stores location data and supports complex spatial queries.
[] 6. Deployment
[] What: A centralized Command Center (Web App) and containerized backend services.
[] How: The full stack is containerized using Docker and deployed via Docker Compose.

[] 1: procedure MapHazard(BBox, Telemetry)

[] 4: GroundDist ← PixelOffset * (Telemetry.Alt / FocalLength)
[] 5: Lat_d ← Telemetry.Lat + (GroundDist.Y * cos(Telemetry.Yaw))
[] 6: Long_d ← Telemetry.Long + (GroundDist.X * sin(Telemetry.Yaw))
[] 7: SaveToDB(Lat_d, Long_d)
[] 8: return {Lat_d, Long_d}
[] 9: end procedure
[] Autonomous Alert Severity Scoring
[] Input: Material Type, Object Size, Location
[] Output: Severity Level (Critical, High, Medium)
[] Pseudocode:
[] 1: procedure ScoreHazard(Material, Size, Location)
[] 2: RiskWeight ← GetMaterialWeight(Material) // Metal > Plastic > Paper
[] 3: SizeFactor ← Normalize(Size)
[] 4: LocFactor ← (Location.IsRunway() ? 1.5 : 1.0)
[] 5: FinalScore ← (RiskWeight * 0.6 + SizeFactor * 0.4) * LocFactor
[] 6: if FinalScore > 90 return "Critical"
[] 7: if FinalScore > 70 return "High"
[] 8: return "Medium"
[] 9: end procedure

[] 4.3 Security Techniques
[] SkyRecon implements robust security measures to ensure the integrity of flight data and system access.
[] Authentication (JWT):
[] The system uses JSON Web Tokens (JWT) for stateless authentication.
[] Access tokens expire every 15 minutes, requiring a refresh token to maintain the session.
[] Role-Based Access Control (RBAC):
[] Admin: Full system configuration access.
[] Operator: Can initiate missions and view feeds.
[] Viewer: Read-only access to dashboards.
[] Encryption (TLS & AES):
[] Transmission: All WebSocket streams and API calls are secured using TLS 1.3.
[] Storage: Critical mission logs and user passwords (hashed with bcrypt) are encrypted at rest in PostgreSQL.
[] Attack Prevention:
[] SQL Injection: Prevented by using Django ORM which parameterizes queries.
[] XSS: React automatically escapes content to prevent Cross-Site Scripting.
